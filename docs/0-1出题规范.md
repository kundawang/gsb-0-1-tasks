# 0-1 代码生成题的出题规范

面向"给 starter + 一段需求，让模型从零把功能做出来"这一类题。以下要求是硬性的，
出题前逐条对照；跑 A/B 之前再对照一次。

## 一、题面怎么写才不像 AI 写的

- **用第一人称、口语**：像同事在工位上跟你说需求，有业务动机、有抱怨、有取舍。不要"作为一名开发者…"，
  不要"本系统旨在…"，不要通篇排比句。
- **长短句混着来**：允许一句话里带括号补充，允许"我试了下 / 我按 8 小时封顶 / 先这样"这种口头语。
  不要每段都等长、不要每条都五个字对仗。
- **不要把需求写成设计稿**：说清楚"要什么效果、什么边界"，不要规定内部函数怎么拆、文件怎么命名。
- **技术约束要写死**：技术栈、能不能引依赖、产物形态（静态页面 / 单个可执行脚本 / 库）、怎么跑起来。
  比如"纯静态，原生 ES module，不引构建、不装依赖""后端只用标准库"。
- **不要 emoji、不要"总而言之""希望对你有帮助"**这类收尾。
- 允许留一点"你自己定，但要写进 README"的自由度（比如大数怎么表示、存档怎么迁移），
  这类地方要在题面里明确"必须能自证"（README 写清楚、或用测试覆盖）。

## 二、题面必须包含的内容

1. **要做什么**：核心玩法的两三句话，以及一个能想象出来的使用场景。
2. **可判定的硬指标**：
   - 数值/公式/单位（tick 间隔、倍率、上限、舍入规则、时间单位）；
   - 边界（上限、超限怎么处理、空输入、重复操作、时间回溯）；
   - 状态与持久化（存档格式、版本号、老存档迁移、离线结算的输入输出）；
   - 确定性（随机走 seed；同 seed + 同一串操作 + 同一段时间 ⇒ 结果完全一致）。
3. **可测性**：哪些部分必须是"纯逻辑、可单测"（产出计算、结算、排序、解析），
   要求用项目自带的测试手段覆盖（`node --test`、`pytest` 等），并且原始 starter 里的冒烟用例不能删。
4. **运行方式**：一条命令能跑起来；不许联网、不许外部服务；不许悄悄改端口/路径约定。
5. **交付形态**：产物文件放哪、README 要写什么（怎么跑、怎么存档、关键决策）。

## 三、starter（初始环境）放什么

- 一个**能跑起来**的最小骨架：入口文件、目录结构、配置文件、1~2 个冒烟用例。
- 题面里提到的数据文件（表格/JSON）如果要固定，就放在 starter 里，并在题面里点明路径。
- **不要**放：答案、参考实现、TODO 清单（等于把实现步骤喂给模型）、额外依赖、被注释掉的核心逻辑。
- starter 要干净：不含 `node_modules`、`.venv`、数据库文件、日志、构建产物。

## 四、难度怎么把握

- 简单（不收录为主）：只有一个模块、逻辑一页纸能写完。
- **中等（推荐）**：跨 2~4 个模块（数据层 + 计算 + 界面/输出），有状态与边界，有存档或迁移，
  纯逻辑部分必须有测试。
- 困难：并发/异步、协议/序列化、性能约束、跨进程状态。

判定标准以实跑结果为准（有效轮数、实现质量），出题时只给"预计"。

## 五、出题前自检清单

- [ ] 题面是口语的第一人称，读起来像同事说的，不是规格书。
- [ ] 所有硬指标（数值/边界/单位/上限）都写了，且能判定。
- [ ] 纯逻辑部分明确要求可测，并保留 starter 的冒烟用例。
- [ ] 随机/时间相关行为要求确定性（seed、传入时间段而非等时钟）。
- [ ] starter 能一条命令跑起来，且不含答案与 TODO。
- [ ] 不联网、不依赖外部服务。
- [ ] 题面里的每一句话，都能在验收清单里找到对应判定点（或明确写了"自由发挥，但要写进 README"）。
