# 0-1 题目验收清单（通用模板）

每题把下面这份拷到 `tasks/T<编号>/rubric.md`，按题面逐条具体化（写清输入与期望输出）。
判定以"能跑、能看、能复现"为准，不靠印象。

## 1. 跑起来

- [ ] 按 README 里写的那条命令能直接跑起来（首次运行不联网、不额外装依赖）。
- [ ] 运行没有任何报错；控制台/页面能看出核心流程在工作。

## 2. 核心逻辑（纯逻辑部分，必须可测）

- [ ] 项目自带的测试命令能跑通（`node --test` / `python -m pytest -q` 等），starter 里的冒烟用例没被删。
- [ ] 题面里的每条数值/公式/单位都能在测试里找到对应用例（给出输入 → 期望输出）。
- [ ] 随机行为走 seed：同 seed + 同一串操作，结果逐字节一致（或数值完全一致）。

## 3. 边界与异常

- [ ] 空输入、极值（0、负数、超大数）、重复操作、时间回溯/离线结算，各自有明确行为且不崩。
- [ ] 上限类规则（封顶、配额、容量）真的生效，超限时的行为与题面一致。
- [ ] 非法输入有可读提示，不是静默吞掉。

## 4. 状态与持久化

- [ ] 存档/导出能用，重新导入后状态一致。
- [ ] 带版本号的存档能迁移旧版本；缺字段补默认值（不能被清空）。
- [ ] 迁移/重算逻辑有测试覆盖。

## 5. 与题面逐条对照

- [ ] 把题面里每个"要求/要点"列成一行，逐条勾：实现了 / 部分实现 / 没做，并写一句证据（命令输出或文件）。
- [ ] 题面里说"你自己定"的地方：README 里有没有写清楚决定与理由。

## 6. 代码卫生（不直接判分，但影响"实现好不好"）

- [ ] 没有为了凑结构而堆的无意义抽象/空文件。
- [ ] 没有复制粘贴的大段重复逻辑。
- [ ] 注释解释"为什么"，不是逐行复述代码。
- [ ] 没有把答案/调试代码留在产物里。

## 7. 记录（判 A/B 用）

- [ ] A 轮：产物快照分支 + 轨迹 jsonl 已记账（`t record`）。
- [ ] B 轮：同上。
- [ ] A/B 差异点写清楚：跑了哪些命令、测试通过数、产物里关键的实现差异、有没有偷工减料（比如把需求写死成常量）。
